### GMS Backend (main)

**Tech stack:** FastAPI, SQLAlchemy 2.0, PostgreSQL (psycopg3), Alembic, JWT (python-jose), bcrypt, Pydantic v2

**Models:**
- `User` — id, email, name, password_hash, role (admin/manager/member), manager_id (self-ref FK), team_id
- `Team` — id, name, manager_id
- `Goal` — id, title, description, level (company/team/individual), status (8 states), tag (daily→yearly), priority (critical/high/medium/low), weightage (auto from priority), start_date, due_date (auto from tag), creator_id, assignee_id, team_id, completion_percentage
- `Subtask` — id, goal_id, title, description, is_completed, completed_at
- `Progress` — id, goal_id, completion_percentage, notes, updated_at

- `Score` — id, goal_id, rating (below/meets/above expectations), scored_by

**Goal lifecycle:**
```
DRAFT → PENDING_APPROVAL → ACTIVE → AWAITING_FEEDBACK → SCORABLE → SCORED
                                  ↘ COMPLETED
         ↘ REJECTED
```
(Admin/Manager assigning directly → skips to ACTIVE)

**Weightage system:** Priority maps to fixed % (critical=40, high=30, medium=20, low=10). Total per user per tag period cannot exceed 100%.

**API routes:**
- `POST /api/v1/auth/login`
- `GET/POST /api/v1/users/`, `GET/PATCH/DELETE /api/v1/users/{id}`

- `GET /api/v1/users/{user_id}/weightage/{tag}`

**Permissions:**
- Admin: full access

2. Due date auto-calculated from start_date + tag duration

5. At-risk = time elapsed > 70% AND completion < 50%
6. Manager assigning goal to team member → auto-ACTIVE (no approval needed)

### 4.1 Goal Management Service (GMS)

**Responsibilities:**
- CRUD operations for goals
- Hierarchical goal structure (Company → Team → Individual)
- Goal approval workflow management
- Weightage validation (total must = 100%)
- Progress tracking and aggregation
- Goal versioning and history

**Key Entities:**
```
Goal
├── id
├── title
├── description
├── hierarchy_level (COMPANY, TEAM, INDIVIDUAL)
├── parent_id (for hierarchy)
├── weightage (0-100)
├── owner_id (Employee or Manager)
├── status (DRAFT, PENDING_APPROVAL, ACTIVE, COMPLETED, ARCHIVED)
├── created_at
├── updated_at
└── created_by

GoalApproval
├── id
├── goal_id
├── approver_id (Manager or Admin)
├── approval_status (PENDING, APPROVED, REJECTED)
├── feedback
├── approved_at

GoalProgress
├── id
├── goal_id
├── completion_percentage (0-100)
├── notes
├── updated_by
├── updated_at

GoalHistory
├── id
├── goal_id
├── change_type (CREATED, UPDATED, APPROVED, COMPLETED)
├── changed_by
├── changed_at
└── previous_values (JSON)
```

**API Endpoints:**
```
POST   /api/v1/goals                 # Create goal
GET    /api/v1/goals                 # List goals (with filters)
GET    /api/v1/goals/:id             # Get goal details
PUT    /api/v1/goals/:id             # Update goal
DELETE /api/v1/goals/:id             # Archive goal (soft delete)
POST   /api/v1/goals/:id/submit      # Submit for approval
POST   /api/v1/goals/:id/approve     # Approve goal
POST   /api/v1/goals/:id/reject      # Reject goal
PUT    /api/v1/goals/:id/progress    # Update progress %
GET    /api/v1/goals/stats/team      # Get team goal stats
GET    /api/v1/goals/stats/company   # Get company goal stats
```

**Workflow State Machine:**
```
DRAFT ──submit──&gt; PENDING_APPROVAL ──approve──&gt; ACTIVE ──complete──&gt; COMPLETED ──archive──&gt; ARCHIVED
                       │ reject                                            │ reopen
                       └──────────────────────────────────────────────────┘
```

├── id

├── reminder_count

```

**Scheduler Job:**
```
Every 6 hours:
  1. Get all employees in probation
  2. Calculate working days since DOJ
  3. For each trigger point (30, 60, 80):
     - If working days reached: create forms + send email
     - If triggered but not submitted:
       - +2 days: send reminder 1
       - +4 days: send reminder 2
       - +6 days: send reminder 3
       - +7 days: escalate to Admin
```

5.1 Probation Monitoring
Automated email triggers go out from the employee&#39;s date of joining (DOJ) at Day 30, Day 60, and
Day 80. Each trigger sends one form to the employee (self-feedback) and one to their manager.
Submissions are stored and cross-shared between employee and manager upon completion.
• Day 30 — initial check-in form
• Day 60 — mid-probation form
• Day 80 — final form, 10 days before confirmation discussion
• Reminder at +2 days if not submitted; escalation to Admin after 7 days
• Day 85–90 — Admin reviews all feedback and shares insights with manager before
confirmation call
Edge Case Handling — Probation
• Leave during probation: probation clock pauses on leave, resumes on return. Admin
dashboard shows &#39;Paused&#39; badge with revised expected trigger date.
• Manager change mid-probation: pending forms reassigned to new manager; prior
submissions visible in read-only probation history with context note.
• Early termination: all pending triggers auto-cancel with audit log entry.
• Cross-share logic: forms only cross-shared after both parties submit. Status shown as
&#39;Waiting for [Manager/Employee]&#39; until then.
• No manager assigned: trigger blocked, Admin alerted with one-click resolution.
• Backdated DOJ: system prompts Admin to send missed forms or mark as waived; waiver
logged for audit. Never auto-fires without confirmation.

Bi-Annual (majority of employees)

Quarterly (select roles / leadership)
• Q1 (Jan–Mar): Trigger Apr 1, close Apr 15
• Q2 (Apr–Jun): Trigger Jul 1, close Jul 15
• Q3 (Jul–Sep): Trigger Oct 1, close Oct 15
• Q4 (Oct–Dec): Trigger Jan 1, close Jan 15
Reminder schedule for all cycles: 5th (gentle nudge), 15th (urgent), 22nd (escalation to Admin if

**Scheduler Job:**

```

Every 6 hours:

  1. Get all employees in probation

  2. Calculate working days since DOJ

  3. For each trigger point (30, 60, 80):

     - If working days reached: create forms + send email

     - If triggered but not submitted:

       - +2 days: send reminder 1

       - +4 days: send reminder 2

       - +6 days: send reminder 3

       - +7 days: escalate to Admin

```

### 9.2 Probation Workflow

```

Employee Joins (DOJ tracked)

       │

       ▼ (Day 30 reached)

Forms Triggered

├── Employee self-feedback form

└── Manager feedback form

       │

       ▼ (User submits)

Submitted (awaiting peer)

       │

       ├─ If NOT submitted after 7 days: ESCALATE to Admin

       │        ├── Reminder 1: +2 days

       │        ├── Reminder 2: +4 days

       │        ├── Reminder 3: +6 days

       │        └── Escalate: +7 days

       │

       └─ Once both submitted: CROSS-SHARE feedback

       │

       ▼ (Repeat for Day 60 &amp; Day 80)

Final Status:

├── On Day 85-90: Admin reviews &amp; shares insights

├── Probation Confirmed: Employee cleared

└── Probation Rejected: Employee offboarding

```

```

Admin Initiates Cycle (e.g., Q1 2026)

       │

       ▼

       │

       ▼

       │

       ▼

Manager Review Phase

├── Managers review employee self-assessment

├── Provide manager feedback

└── Set final rating

       │

       ▼

Feedback Cross-Share

├── Both submitted: Share results

└── Pending: Send reminders

       │

       ▼

Close Cycle

Before you start writing the code, I want to put on my Staff Engineer hat and point out a few &quot;Pro&quot; architectural edge cases within this plan that we should address now to prevent nasty bugs in production.

1. The Multi-Pod Scheduler Trap (Phase 6)
You plan to use AsyncIOScheduler running inside the FastAPI startup event.

The Danger: Your High-Level Design (HLD) mentioned running multiple Backend Pods behind a Load Balancer. If you run an in-memory APScheduler in every pod, every pod will fire the triggers. If you have 3 pods running, the employee will receive three &quot;Day 30 Probation&quot; emails simultaneously.

The Pro Fix: You must configure APScheduler to use a PostgreSQL Job Store (SQLAlchemyJobStore). This ensures that the scheduler locks the job in the database, guaranteeing that the probation check or review reminder is executed exactly once across the entire cluster.

2. The &quot;Working Days&quot; Calculation Flaw (Phase 3)
The Danger: Counting Monday–Friday is a good baseline, but it ignores public holidays and company-wide closures. If an employee&#39;s probation timer doesn&#39;t account for a 3-day public holiday, triggers will fire prematurely, which can cause HR compliance issues.

The Pro Fix: Create a simple company_holidays table (just id, date, description). Your calculate_working_days() utility should do: (Total Mon-Fri Days) - (Count of holidays falling on Mon-Fri within that date range).

3. Recursive SQLAlchemy Queries for Goals (Phase 2 &amp; 7)
The Danger: To calculate the GET /api/v1/dashboard/company stats, you need to aggregate completion percentages from Individual → Team → Company goals. Doing this via standard SQLAlchemy ORM calls will result in an &quot;N+1 query problem,&quot; bringing the database to a crawl as it fetches every child goal individually.

The Pro Fix: We need to use a Recursive CTE (Common Table Expression) in SQLAlchemy. This allows PostgreSQL to traverse the parent_id hierarchy and sum up the weightages and progress in a single, highly performant query before returning the JSON payload to FastAPI.

4. Offset Pagination vs. Cursor Pagination (Phase 10)
The Danger: Using .offset((page - 1) * limit) is fine for Goals or Users (small tables). However, for Notifications and ReviewPerformanceHistory (which will grow massively), deep offsets (e.g., page=500) force PostgreSQL to scan and discard thousands of rows, causing high latency.

The Pro Fix: Use Cursor Pagination (keyset pagination) for the Notifications and History endpoints, using the created_at timestamp or indexed id as the cursor.
